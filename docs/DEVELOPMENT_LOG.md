# 2. 프로젝트 목적

MICU 화재대피 인원배치 프로젝트는 중환자실(MICU) 화재대피 상황에서 근무 중인 인원을 기준으로 대피 역할을 배치하고, 필요한 경우 사용자가 배치를 확인·수정·저장할 수 있도록 지원하는 브라우저 기반 도구를 만드는 것을 목적으로 시작되었다.

초기에는 핵심 배치 기능을 빠르게 검증하는 것이 우선이었다.

이후 프로젝트가 발전하면서 단순한 배치 계산기에서 다음을 함께 다루는 로컬 웹앱 형태로 확장되었다.

- 근무표 입력
- 근무표 보관 및 사용
- 인원 관리
- 자동 배치
- 수동 배치 수정
- 변경 이력
- 로컬 저장
- 전체 백업 및 복원
- 모바일 사용
- 테스트 및 회귀검수
- 실제 운영 자료 반영을 위한 기반 구조

현재 단계에서는 실제 MICU 운영 규칙과 공식 근무표·대피 배치판이 모두 확정된 상태가 아니므로, 기술 구조와 사용 흐름을 먼저 안정화하고 실제 자료 확보 후 실데이터를 반영하는 방향을 유지한다.

# 3. 초기 개발 방향

초기 개발의 핵심 원칙은 다음과 같았다.

1. 핵심 배치 기능을 먼저 구현한다.
2. 실제 사용 흐름을 고려하되 실제 운영 규칙이 없는 부분은 임의로 확정하지 않는다.
3. 브라우저에서 별도 서버 없이 사용할 수 있는 가벼운 구조를 우선한다.
4. 기능이 안정된 뒤 구조를 개선한다.
5. 새로운 기능을 추가할 때 기존 기능의 회귀를 함께 확인한다.
6. 실제 운영 자료가 확보되기 전까지는 가상의 규칙을 과도하게 확장하지 않는다.

```text
사용자 입력

↓
IndexedDB
↓
새로고침 / 재실행
↓
복원
```

이라는 데이터 수명주기를 고려해야 했기 때문이다.

# 5. 근무표 Parser 개선

근무표 입력 과정에서는 Excel 파일의 구조가 항상 동일하다고 가정하지 않도록 Parser를 발전시켰다.

주요 방향:

- 날짜 행 탐색
- 이름 열 탐색
- 사용자가 필요한 경우 행·열 직접 지정
- 날짜 중복 검사
- 날짜 순서 검사
- 누락 날짜 검사
- 빈 이름 행 검사
- 미확인 근무 코드 경고
- 빈 칸 경고
- 해석 결과를 저장하는 snapshot 개념

이 단계의 중요한 판단은 다음과 같다.

> Excel을 읽는 문제와 화재대피 배치를 계산하는 문제를 분리한다.

따라서 Parser가 변경되더라도 배치 Domain 로직을 불필요하게 변경하지 않는 방향으로 발전시켰다.

실제 MICU 공식 근무표가 확보되기 전에는 Parser를 가상의 양식에 맞춰 무한히 확장하지 않는다.

# 6. IndexedDB 선택과 저장 구조

프로젝트가 브라우저 기반 단일 사용자 도구로 발전하면서 새로고침 이후에도 데이터를 유지할 필요가 생겼다.

초기 단순 상태 저장만으로는 다음 요구를 충족하기 어려웠다.

- 여러 근무표 보관
- 사람별 수정 저장
- 수동 배치 저장
- 변경 이력 저장
- 전체 백업
- 복원

이에 따라 IndexedDB를 로컬 영속 저장소로 사용했다.

현재 저장 구조의 핵심 원칙은 다음과 같다.

```text
UI
↓
Application State
↓
Storage Boundary
↓
IndexedDB
```

UI가 저장소의 내부 구조를 직접 조작하기보다 저장 경계를 통해 데이터를 저장·조회하는 방향으로 발전시켰다.

또한 저장 성공 여부를 단순히 write 호출의 성공만으로 판단하지 않고, 필요한 경우 재읽기와 revision 정보를 이용해 데이터 상태를 확인하도록 발전시켰다.

---

# 7. 수동 배치와 변경 이력

자동 배치만으로는 실제 사용 과정에서 발생할 수 있는 예외적인 인원 배치를 충분히 표현하기 어렵다는 점을 고려하여 수동 배치 기능을 추가했다.

핵심 원칙:

> 사용자가 명시적으로 수정한 배치는 자동 계산보다 우선한다.

이 과정에서 단순히 화면의 배치 배열을 수정하는 것보다 "무엇이 변경되었는가"를 추적할 필요가 생겼다.

따라서 변경 이벤트와 Audit/History 영역을 분리했다.

주요 기록 대상:

- 인원 이름 변경
- 인원 역할 변경
- 인원 추가·제외 관련 변경
- 수동 배치 변경
- 저장 성공/실패
- 백업 및 복원 관련 작업

이 구조는 이후 버전에서 수정 이력 조회와 내보내기로 확장되었다.

# 8. 백업 및 복원 구조

프로젝트가 로컬 저장에 의존하게 되면서 브라우저 저장공간에만 데이터를 두는 것에는 한계가 생겼다.

따라서 전체 상태를 외부 파일로 내보내고 다시 복원하는 백업 구조를 추가했다.

백업에는 단순히 현재 화면만 저장하는 것이 아니라 프로젝트의 핵심 운영 상태를 함께 보존하는 방향을 사용한다.

주요 원칙:

- 백업 포맷에 명시적인 formatVersion을 둔다.
- 데이터 구조를 검증한 뒤 복원한다.
- 손상된 파일을 거부한다.
- 복원 전 현재 상태를 보호한다.
- 복원 과정에서 다른 탭의 오래된 상태가 최신 데이터를 덮어쓰지 못하도록 한다.
- 복원 후 다시 읽어 결과를 검증한다.
- 백업 형식이 바뀌면 migration 필요성을 검토한다.

이 구조는 단순한 파일 다운로드 기능이 아니라 데이터 수명주기의 일부로 취급한다.

따라서 다음과 같이 책임을 분리했다.

```text
domain

├─ 백업 포맷

storage

audit

└─ 화면 상태와 전체 흐름 연결
```

중요한 원칙은 다음과 같다.

> 구조를 바꾸기 위해 기능을 다시 만드는 것이 아니라, 이미 동작하는 기능을 유지하면서 책임을 분리한다.

- 문서와 실제 구조의 일치 여부 점검

v0.7.3의 중요한 의미는 새로운 대형 기능을 추가한 버전이라기보다, 이후 기능 개발을 안전하게 진행하기 위한 구조적 기준점을 만든 버전이라는 것이다.

현재 판단에서는 v0.7.3의 코드 구조 자체를 다시 크게 수정할 필요가 있는 문제는 확인되지 않았다.

- 전체 화면 흐름

# 12. 현재 확인된 한계

현재 프로젝트에는 다음과 같은 미확정 영역이 존재한다.

### 실제 MICU 운영 자료

실제 운영 근무표와 실제 화재대피 배치판을 확보하기 전까지는 현재 Parser와 배치 규칙을 공식 운영 규칙으로 간주하지 않는다.

### 실제 모바일 기기

에뮬레이터에서 확인된 동작과 실제 Android/iPhone에서의 전체 동작을 동일하게 취급하지 않는다.

### 실제 병원 운영 승인

현재 프로그램은 기술적 프로토타입이며 병원 공식 운영 도구 또는 임상적 의사결정 도구로 승인된 상태가 아니다.

### 다중 사용자

현재는 서버와 계정 시스템을 사용하는 다중 사용자 애플리케이션이 아니다.

---

# 13. 중요한 설계 원칙

현재까지 프로젝트에서 유지해야 할 중요한 원칙은 다음과 같다.

## 13.1 UI를 업무 규칙의 유일한 원천으로 만들지 않는다

화면 코드에만 중요한 규칙을 두지 않는다.

## 13.2 기존 기능을 유지하면서 개선한다

새 기능을 만들기 위해 기존 기능을 불필요하게 다시 작성하지 않는다.

## 13.3 저장 상태와 화면 상태를 구분한다

화면에 보이는 값과 영속적으로 저장된 값이 항상 동일하다고 가정하지 않는다.

## 13.4 수동 변경은 명시적인 상태로 취급한다

자동 계산 결과와 사용자의 수동 수정 결과를 구분한다.

## 13.5 백업은 데이터 수명주기의 일부다

백업은 부가 기능이 아니라 저장·복원 신뢰성을 위한 핵심 기능으로 취급한다.

## 13.6 실제 자료가 없으면 가정을 확정하지 않는다

실제 MICU 근무표와 운영 규칙이 확보되기 전에는 임의의 규칙을 공식 규칙처럼 고정하지 않는다.

## 13.7 구조 개선은 필요할 때만 한다

코드가 더 예뻐 보인다는 이유만으로 안정적인 구조를 다시 작성하지 않는다.

# 14. v0.7.4의 개발 방향

v0.7.3 이후에는 기능 수를 빠르게 늘리기보다 안정성 검증을 우선한다.

현재 제안되는 방향:

1. 백업·복원 경계조건 보강
2. 추가 인원이 수동 배치된 상태의 백업/복원 검증
3. 저장·복원 회귀검사 강화
4. 다중 탭 및 오래된 상태의 저장 충돌 검증
5. 실제 Android/iPhone/Windows 환경 검증
6. 현재 상태 관리 구조의 유지 가능성 재평가
7. 실제 운영 자료 확보 전까지 Parser를 과도하게 확장하지 않음

v0.7.4에서는 대규모 구조 재작성보다 v0.7.3에서 정리한 구조가 실제 조건에서 안정적인지 확인하는 것을 우선한다.

# 20. 기록의 신뢰성 원칙

이 문서에는 확인되지 않은 개발 역사를 사실처럼 추가하지 않는다.

과거 대화, 코드, 테스트 보고서 또는 프로젝트 문서에서 확인되지 않은 내용은 추정하여 기록하지 않는다.

과거 결정의 이유가 확인되지 않는 경우에는 "이유 미상" 또는 "기존 결정으로 유지"라고 기록하고, 필요할 때 별도로 결정 로그를 만든다.

개발 기록의 목적은 과거를 미화하거나 모든 결정을 정당화하는 것이 아니라, 이후 개발자가 프로젝트의 현재 상태와 결정 맥락을 이해할 수 있도록 하는 것이다.
