## 1. v0.7.4의 목적

v0.7.4는 기능을 많이 추가하는 버전이 아니라, v0.7.3에서 만들어 놓은 기능을 안전하게 유지하면서 앞으로의 개발을 안정적으로 이어가기 위한 기반 강화 버전이다.

한 문장으로 표현하면:

> v0.7.3까지 만들어 놓은 기능을 깨뜨리지 않으면서, 앞으로의 개발을 안전하게 할 수 있는 기반을 만드는 버전.

따라서 v0.7.4에서 실제로 무엇을 수정하거나 추가할지는 처음부터 정해 놓지 않는다.

먼저 현재 코드와 동작을 다시 확인하고, 실제로 위험하거나 불안정한 부분을 찾아낸 뒤 우선순위를 정해 작업한다.

## 2. 개발의 기본 원칙

### 2.1 먼저 확인하고 나중에 수정한다

기능을 바로 코딩하지 않는다.

항상 다음 순서를 따른다.

1. 현재 동작 확인
2. 관련 코드 확인
3. 영향 범위 확인
4. 위험 분석
5. 작업 필요성 판단
6. 최소 변경 계획 수립
7. 구현
8. 자동 테스트
9. 기존 기능 회귀 테스트
10. UI/환경 검증
11. 문서화
12. 버전 기록

### 2.2 정상 동작을 먼저 정의한다

v0.7.3의 현재 동작을 기준선으로 삼는다.

새 기능이나 수정 때문에 기존 기능이 달라졌다면 그것이 의도된 변경인지, 의도하지 않은 회귀인지 구분한다.

### 2.3 큰 리팩터링을 목적으로 하지 않는다

코드가 조금 불편해 보인다는 이유만으로 구조를 크게 바꾸지 않는다.

특히 현재 구조의 핵심인 다음 영역은 실제 문제가 확인될 때만 변경한다.

- script.js의 UI 상태 관리
- IndexedDB 저장 구조
- domain 모델
- parser/model 분리
- audit/history 구조
- backup/restore 형식

### 2.4 확인하지 않은 것은 사실로 기록하지 않는다

다음 상태를 구분한다.

- CONFIRMED: 실제 동작 또는 자료로 확인
- CODE-VERIFIED: 코드 분석으로 확인
- INFERRED: 코드/자료를 근거로 추론
- UNVERIFIED: 아직 확인하지 않음
- BLOCKED: 환경이나 자료 부족으로 확인 불가

특히 실제 MICU 운영 규칙, 공식 근무표 형식, 실제 모바일 기기 동작 등은 확인 전까지 공식 사실로 취급하지 않는다.

# 12. STEP 9. 버전 검토

v0.7.4가 실제로 안정화되었는지 판단한다.

### PASS
- 핵심 기능 정상
- 자동 테스트 통과
- 관련 회귀 테스트 통과
- 알려진 치명적 문제 없음

### PASS WITH ISSUES
- 핵심 기능은 정상
- 일부 제한 또는 미검증 환경 존재
- 릴리스는 가능하지만 제한사항 기록 필요

### BLOCKED
- 필요한 환경/자료가 없어 중요한 검증을 완료할 수 없음

### FAIL
- 핵심 기능 실패
- 데이터 손실 가능성
- 중대한 회귀
- 해결되지 않은 핵심 버그

# 15. v0.7.4에서 특히 주의할 위험

현재 프로젝트에서 실제로 중요한 위험은 다음과 같다.

### 15.1 상태 관리 복잡성

script.js에 UI 상태가 많이 존재하므로 작은 UI 변경이 다른 기능에 영향을 줄 수 있다.

대응:
- 상태 흐름을 먼저 확인
- 변경 범위를 작게 유지
- 실제 문제가 확인될 때만 분리

### 15.2 IndexedDB 데이터 손상/복원 문제

이 프로젝트는 브라우저 로컬 저장을 사용하므로 저장/복원은 단순 UI 기능이 아니라 핵심 데이터 보호 영역이다.

대응:
- 저장 실패
- 복원 실패
- 기존 데이터 호환
- 여러 탭 충돌
- 새로고침 후 상태
를 계속 회귀 테스트한다.

### 15.3 자동 배치와 수동 override 충돌

수동으로 지정한 배치가 자동 계산에 의해 덮어써지면 안 된다.

대응:
- manual override 우선 원칙 유지
- 자동 재계산 후에도 override가 보존되는지 확인

### 15.4 규칙 변경에 따른 기존 데이터 영향

새로운 규칙 프로필을 추가할 때 기존 roster의 의미가 바뀌면 안 된다.

대응:
- 기존 snapshot 보존
- 새 규칙은 additive 방식 우선
- 기존 데이터 재계산 여부를 명시적으로 관리

### 15.5 실제 병원 운영자료와의 차이

현재 내부 규칙은 공식 병원 규칙으로 승인된 것이 아니다.

대응:
- 실제 MICU Excel과 공식 대피 규칙 확보 전까지 기술적 검증과 운영 검증을 구분한다.

### 15.6 모바일 미검증

현재 모바일은 일부 확인됐지만 실제 기기 및 restart 안정성이 충분히 검증되지 않았다.

대응:
- 미검증 상태를 PASS로 바꾸지 않는다.
- 실제 기기 확보 후 별도 acceptance test를 수행한다.

# 16. 사용자가 “시작하자”라고 하면 실행할 순서

앞으로 사용자가 정확히 “시작하자”라고 하면 다음 순서로 진행한다.

### 첫 번째
현재 v0.7.3 RC 프로젝트 파일을 다시 확인한다.

### 두 번째
AI_QA_GUIDELINES.md와 REGRESSION_BASELINE.md를 기준으로 현재 상태를 점검한다.

### 세 번째
v0.7.3의 실제 코드 구조와 테스트를 다시 분석한다.

### 네 번째
v0.7.4 Risk Analysis를 작성한다.

### 다섯 번째
실제 작업 후보를 우선순위화한다.

### 여섯 번째
사용자에게:
- 무엇이 문제인지
- 왜 중요한지
- 무엇을 바꿀지
- 기존 기능에 어떤 영향이 있는지
- 다른 방법은 무엇인지
를 설명한다.

### 일곱 번째
사용자가 진행을 확인하면 첫 번째 작업부터 구현한다.

### 여덟 번째
구현 → 자동 테스트 → 회귀 테스트 → 문서화 순서로 진행한다.

### 아홉 번째
작업이 끝날 때마다 결과를 기록하고 다음 작업으로 넘어간다.

# 17. 개발 진행 방식

이 프로젝트에서는 여러 파일을 한꺼번에 바꾸지 않는다.

원칙:

> 분석은 한 번에 넓게, 변경은 한 번에 작게.

즉, 전체 구조는 먼저 충분히 분석하되 실제 파일 수정은 필요한 범위만 최소 단위로 진행한다.

사용자는 매 단계에서 다음을 확인할 수 있다.

- 지금 무엇을 하는지
- 왜 하는지
- 기존 기능에 영향이 있는지
- 어떻게 검증하는지
- 다음에 무엇을 하는지

# 18. v0.7.4의 완료 기준

v0.7.4는 단순히 코드가 실행된다고 완료하지 않는다.

다음 조건을 만족해야 한다.

- 실제 변경 목적이 명확하다.
- 변경 전 영향 분석이 있다.
- 기존 기능의 회귀 여부를 확인했다.
- 자동 테스트가 통과했다.
- 필요한 UI/환경 테스트를 완료했다.
- 미검증 사항을 명시했다.
- 버그와 제한사항을 기록했다.
- 관련 문서가 실제 구현과 일치한다.
- v0.7.4의 변경 이력이 남아 있다.
- 다음 버전의 기준선으로 삼을 수 있다.

# 19. v0.7.4 이후

의 흐름을 반복한다.

- 더 세분화된 상태 관리
- 실제 모바일 acceptance test
- 공식 MICU 근무표 반영
- 공식 화재대피 규칙 반영
- 서버/다중 사용자 구조
