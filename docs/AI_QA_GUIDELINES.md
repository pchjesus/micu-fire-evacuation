# AI 개발·QA 및 회귀검수 지침

문서 버전: 1.0
적용 기준: MICU 화재대피 인원배치 v0.7.3 RC 이후
문서 목적: AI가 이후 버전의 개발 결과를 일관된 절차로 검수하고, 검수 결과를 다음 개발의 공식 기록과 기준선으로 연결하기 위한 지침

---

## 1. 목적

이 문서는 MICU 화재대피 인원배치 프로젝트에서 AI가 수행하는 개발 결과 검수(QA)의 절차와 판단 기준을 정의한다.

검수의 목적은 단순히 새 기능이 작동하는지 확인하는 것이 아니다.

다음 사항을 함께 확인한다.

- 요구한 신규 기능이 의도대로 동작하는가
- 기존에 정상 동작하던 기능이 유지되는가
- 새 기능과 기존 기능 사이에 충돌이 발생하지 않는가
- 저장·복원·새로고침·재실행 과정에서 데이터가 보존되는가
- 경계조건과 오류조건에서 안전하게 동작하는가
- UI/UX가 기존 기능을 방해하거나 사용성을 떨어뜨리지 않는가
- 코드 구조와 실제 동작이 프로젝트의 아키텍처 원칙에 맞는가
- 문서와 실제 구현이 일치하는가
- 이전 버전의 검수 결과가 다음 버전에서도 추적 가능한가
- 발견된 문제와 해결 과정이 공식 개발 기록으로 남는가

검수는 프로젝트의 기존 「구현 및 위험 검토」 지침과 AI-Assisted Software Development Skill을 보완한다.

---

## 2. 기본 원칙

### 2.1 이해한 뒤 검수한다

새 버전을 받으면 현재 버전, 직전 버전, 변경사항, 구조, 데이터 모델, 테스트, 문서를 먼저 확인한다.

코드 일부만 보고 전체 동작을 판단하지 않는다.

### 2.2 새 기능보다 회귀를 함께 본다

새 기능이 정상적으로 작동하더라도 기존 기능이 영향을 받았다면 검수 통과로 판단하지 않는다.

검수는 다음 두 축을 모두 포함한다.

```text
신규 기능
+
기존 기능 회귀
```

### 2.3 확실한 사실과 추론을 구분한다

검수 결과는 다음을 구분한다.

- 실제 테스트로 확인된 사실
- 코드 분석을 통해 강하게 추론되는 내용
- 가능성이 있는 문제
- 현재 환경에서 검증하지 못한 내용

검증하지 못한 환경을 정상이라고 기록하지 않는다.

### 2.4 기존 구조를 불필요하게 바꾸지 않는다

검수 과정에서 코드가 더 깔끔해 보인다는 이유만으로 구조 변경을 요구하지 않는다.

실제 버그, 유지보수 문제, 기능 확장에 대한 장애, 과도한 결합 등 명확한 이유가 있을 때만 구조 개선을 제안한다.

### 2.5 검수와 수정은 분리한다

기본 검수 작업에서는 코드를 임의로 수정하지 않는다.

검수에서 문제를 발견하면 먼저 보고한다.

사용자가 수정 또는 구현을 지시한 뒤에만 수정 작업으로 넘어간다.

## 3. 검수 대상

새 버전 검수에서는 가능한 범위에서 다음 영역을 확인한다.

1. 프로젝트 구조
2. Domain / 업무 규칙
3. 근무표 Parser
4. 인원 모델
5. 배치 계산
6. UI
7. Storage / IndexedDB
8. Audit / 수정 이력
9. Backup / Restore
10. 변경 이벤트
11. 신규 기능
12. 기존 기능
13. 테스트 코드와 테스트 결과
14. 문서
15. 배포물 및 버전 정보

프로젝트가 실제로 사용하는 영역만 검수한다. 존재하지 않는 기능을 검수 대상으로 가정하지 않는다.

---

## 4. 검수 시작 전 확인

새 버전을 검수할 때 다음 정보를 먼저 확립한다.

- 현재 버전
- 직전 기준 버전
- 주요 변경사항
- 현재 아키텍처
- 데이터 모델
- 저장 방식
- 주요 UX 결정
- 기존 테스트
- 기존에 알려진 문제
- 이전 검수 결과
- 실제 검증 가능한 환경

현재 v0.7.3의 주요 기준은 다음과 같다.

- 서버 없이 브라우저에서 동작하는 단일 사용자 도구
- Domain / UI / Storage / Audit의 책임 분리
- 근무표 Parser와 모델 분리
- 변경 이벤트와 백업 포맷 분리
- IndexedDB 기반 저장
- 전체 백업 및 복원
- 수정 이력 기록
- 기존 결과를 유지하는 것을 우선하는 구조 개선
- 실제 Android/iPhone 및 Windows Chrome 검증은 별도 확인 대상

위 내용은 이후 버전에서 변경될 수 있으므로 새 버전의 실제 문서와 코드가 우선한다.

## 5. 직전 버전과의 비교

가능하면 직전 버전과 새 버전을 직접 비교한다.

비교 대상:

- 파일 추가
- 파일 삭제
- 파일 이동
- 코드 변경
- 데이터 구조 변경
- 저장 구조 변경
- UI 변경
- 테스트 변경
- 문서 변경
- 설정 변경

특히 다음 변경은 영향 분석을 우선한다.

- Domain 로직 변경
- Storage 변경
- Backup 포맷 변경
- ID 구조 변경
- 상태 관리 변경
- 저장·복원 흐름 변경
- 공용 함수 변경
- UI와 Domain 사이의 연결 변경

변경된 코드만 검사하고 끝내지 않는다. 변경된 코드의 의존 기능도 함께 확인한다.

## 6. 신규 기능 검수

각 신규 기능에 대해 다음을 확인한다.

1. 요구사항대로 동작하는가
2. 정상 입력에서 기대 결과가 나오는가
3. 잘못된 입력을 적절히 차단하거나 경고하는가
4. 빈 값·최소값·최대값 등 경계조건을 처리하는가
5. 저장이 필요한 기능이라면 저장 후 상태가 유지되는가
6. 새로고침 후 유지되는가
7. 필요한 경우 브라우저 재실행 후 유지되는가
8. 기존 기능과 충돌하지 않는가
9. 모바일에서 사용 가능한 구조인가
10. 관련 문서가 실제 동작과 일치하는가

---

## 7. 기존 기능 회귀검수

기존 기능은 단순히 버튼 하나가 작동하는지만 확인하지 않는다.

기능의 전체 흐름을 가능한 범위에서 검사한다.

예:

```text
근무표 등록
→ 확인
→ 저장
→ 사용
→ 인원 수정
→ 배치 수정
→ 저장
→ 새로고침
→ 이력 확인
→ 백업
→ 복원
```

새 기능이 이 흐름의 어느 부분에 영향을 줄 수 있는지 분석한다.

기존 기능이 변경된 경우에는 변경 전 동작과 변경 후 동작을 비교한다.

---

## 8. 저장·복원 검수

저장과 복원은 이 프로젝트의 핵심 안정성 영역으로 취급한다.

가능한 경우 다음을 확인한다.

### 저장

- 정상 저장
- 저장 후 재읽기
- 새로고침 후 유지
- 브라우저 재실행 후 유지
- 저장 실패
- 저장 공간 부족 또는 quota 오류
- 동시 수정
- 중복 저장
- 재시도

### 복원

- 정상 백업 복원
- 손상 파일 거부
- 잘린 JSON 거부
- 지원하지 않는 형식 거부
- 중복 ID 거부
- 깨진 참조 거부
- 복원 전 현재 데이터 보호
- 복원 후 전체 데이터 일치
- 복원 전에 열려 있던 다른 탭의 쓰기 차단
- 복원 실패 시 기존 데이터 보존 여부
- 쓰기 후 재읽기 실패 시 불확실성 표시

검증하지 않은 저장·복원 시나리오는 정상이라고 기록하지 않는다.

---

## 9. 백업 포맷 검수

백업 포맷이 변경된 경우 다음을 확인한다.

- formatVersion이 적절한가
- 새 형식의 필수 필드가 존재하는가
- 잘못된 형식을 차단하는가
- 기존 형식과의 호환 정책이 명확한가
- 필요한 경우 migration이 존재하는가
- 기존 데이터의 의미가 보존되는가
- 추가 인원과 원본 인원이 모두 보존되는가
- 수동 배치가 보존되는가
- 수정 이력이 보존되는가
- 선택된 근무표가 보존되는가

포맷을 변경하면서 이전 백업을 읽는 방법을 정의하지 않은 경우 이를 위험사항으로 기록한다.

---

## 10. 경계조건 및 오류조건

가능한 범위에서 다음을 확인한다.

- 빈 입력
- 누락 입력
- 잘못된 날짜
- 중복 날짜
- 역순 날짜
- 존재하지 않는 ID
- 중복 ID
- 동명이인
- 미확인 근무 코드
- 빈 근무 코드
- 날짜 누락
- 추가 인원
- 제외 인원
- 수동 배치가 존재하는 상태에서의 수정
- 저장 직전 상태 변경
- 다른 탭에서의 변경
- 손상된 백업
- 잘린 데이터
- 예상하지 않은 저장 오류

단, 실제 프로젝트에서 의미가 없는 경계조건을 억지로 추가하지 않는다.

---

## 11. UI/UX 검수

UI 검수는 단순한 미적 선호가 아니라 기능 사용에 영향을 주는 문제를 중심으로 한다.

확인 대상:

- 버튼이 실제 기능과 일치하는가
- 저장·취소·복원 등 중요한 행동의 상태가 명확한가
- 비활성화 조건이 적절한가
- 오류와 경고가 이해 가능한가
- 모달과 스크롤이 정상적으로 작동하는가
- 기존 화면 요소가 새 기능 때문에 가려지거나 충돌하지 않는가
- 모바일 화면에서 주요 기능을 사용할 수 있는가
- 화면 전환 후 상태가 예상과 다르게 초기화되지 않는가

단순히 디자인 취향이 다른 것은 버그로 분류하지 않는다.

---

## 12. 문서와 코드의 일치 검수

다음 문서가 존재한다면 실제 구현과 비교한다.

- README
- SPEC
- ARCHITECTURE
- CHANGELOG
- TEST_REPORT
- RELEASE_REPORT
- MOBILE_ACCEPTANCE
- 개발 기록
- QA 보고서

예:

```text
문서: backups/ 경로
실제 코드: backup/ 경로
→ 문서 불일치
```

이러한 문제는 기능 버그와 구분하여 기록한다.

문서에 존재하지 않는 기능을 실제 기능처럼 작성하지 않는다.

---

## 13. 테스트 결과 검수

자동 테스트가 있는 경우 다음을 확인한다.

- 테스트가 실제로 실행되었는가
- 통과/실패/건너뜀 수가 기록되어 있는가
- 테스트가 변경된 영역을 충분히 다루는가
- 기존 테스트가 삭제되거나 약화되지 않았는가
- 테스트가 실제 동작을 제대로 검증하는가
- 테스트 통과만으로 실제 브라우저/기기 검증까지 완료되었다고 오해하지 않는가

자동 테스트와 실제 환경 테스트는 구분한다.

---

## 14. 검증 수준

검수 결과에는 필요할 경우 다음 상태를 사용한다.

### CONFIRMED

실제 테스트 또는 신뢰할 수 있는 실행 결과로 확인됨.

### CODE-VERIFIED

코드 구조와 로직을 분석해 문제가 없음을 확인했지만 실제 실행 환경 검증은 하지 않음.

### INFERRED

현재 정보로 강하게 추론되지만 직접 검증하지 못함.

### UNVERIFIED

검증할 수 있는 환경이나 자료가 없어 판단하지 못함.

### BLOCKED

환경 문제, 도구 문제, 파일 문제 등으로 검증이 진행되지 않음.

검증하지 못한 항목을 PASS로 기록하지 않는다.

---

## 15. 발견사항 분류

### BUG

현재 동작이 요구사항 또는 기존 정상 동작과 명백하게 다름.

### REGRESSION

이전 버전에서 정상적으로 작동하던 기능이 새 버전에서 깨짐.

### ISSUE

명백한 버그라고 확정할 수는 없지만 위험하거나 추가 확인이 필요한 사항.

### DOCUMENTATION

코드와 문서가 일치하지 않음.

### IMPROVEMENT

현재 동작에는 문제가 없지만 사용성·유지보수성·확장성을 개선할 수 있음.

개선 제안을 버그로 과장하지 않는다.

---

## 16. 심각도

필요한 경우 다음 등급을 사용한다.

### P0 — 중대

데이터 손실, 복원 불가, 핵심 배치 결과 오류 등 프로젝트의 핵심 기능이나 데이터 신뢰성을 심각하게 훼손한다.

### P1 — 높음

주요 기능이 정상적으로 사용되지 않거나 기존 기능에 중요한 회귀가 발생한다.

### P2 — 보통

기능 일부가 잘못되거나 특정 조건에서 문제가 발생하지만 우회가 가능하다.

### P3 — 낮음

사용성 문제, 경미한 UI 문제, 문서 문제 등 즉각적인 기능 장애는 아니다.

심각도는 실제 영향과 재현 가능성을 기준으로 판단한다.

---

## 17. 버그 추적

발견된 버그는 가능한 경우 고유 ID를 부여한다.

예:

```text
BUG-001
REG-001
ISSUE-001
DOC-001
```

버그 ID는 버전이 바뀌어도 유지한다.

예:

```text
BUG-003
최초 발견: v0.7.4
상태: OPEN

수정: v0.7.5
재검증: v0.7.5
상태: FIXED
```

회귀가 다시 발생하면 기존 ID를 연결하여 기록한다.

## 18. QA 보고서

각 의미 있는 버전의 검수 결과는 `QA_REPORT_vX.Y.Z.md` 형식으로 기록한다.

기본 구조:

```text
# QA Report vX.Y.Z

## 1. 검수 대상
## 2. 기준 버전
## 3. 주요 변경사항
## 4. 검수 환경
## 5. 자동 테스트
## 6. 신규 기능 검수
## 7. 기존 기능 회귀검수
## 8. 저장/복원 검수
## 9. 백업 검수
## 10. 경계조건 검수
## 11. UI/UX 검수
## 12. 문서 일치 검수
## 13. 발견된 문제
## 14. 수정 후 재검수
## 15. 미검증/보류 항목
## 16. 최종 판정
## 17. 다음 버전에서 확인할 사항
```

보고서는 단순 테스트 결과가 아니라 해당 버전의 품질 상태와 중요한 판단을 남기는 공식 개발 기록으로 취급한다.

---

## 19. QA 보고서를 공식 개발 기록으로 연결

QA 보고서가 작성되면 필요한 경우 다음 기록과 연결한다.

```text
버전
↓
CHANGELOG
↓
QA_REPORT
↓
BUG / REGRESSION / ISSUE
↓
수정 버전
↓
재검수
```

CHANGELOG에는 중요한 수정·버그·알려진 문제·검수 결과를 간단히 연결한다.

QA 보고서에는 상세한 검수 과정과 근거를 남긴다.

이렇게 하여 나중에 특정 변경이 언제 발생했고 언제 검증되었는지 추적할 수 있도록 한다.

---

## 20. 회귀 기준선에 승격

새 버전에서 새롭게 검증된 중요한 시나리오는 다음 버전부터 회귀검수 기준에 추가할 수 있다.

예:

```text
v0.7.4
추가 인원
→ 수동 배치
→ 전체 백업
→ 복원
→ 데이터 유지 확인
```

이 시나리오가 중요하다고 판단되면 `REGRESSION_BASELINE.md`에 추가한다.

즉 회귀 기준선은 버전이 올라갈수록 검증된 정상 시나리오를 축적한다.

단, 모든 사소한 테스트를 기준선에 추가하지 않는다.

---

## 21. 공식 개발 기록의 신뢰성

QA 보고서와 개발 기록에는 다음을 명확히 기록한다.

- 실제 수행한 테스트
- 수행하지 못한 테스트
- 테스트 환경
- 사용한 fixture
- 자동 테스트 결과
- 실제 기기 테스트 여부
- 추론에 의한 판단
- 남은 위험
- 최종 판정

"문제 없음"이라는 표현은 검증 범위를 넘어선 의미로 사용하지 않는다.

예:

잘못된 기록:

```text
모바일 정상
```

올바른 기록:

```text
Android 16 에뮬레이터에서 편집·저장 확인.
브라우저 재시작 안정성은 검증하지 못함.
실제 Android 기기 미검증.
```

---

## 22. AI가 임의로 해서는 안 되는 것

AI는 다음을 임의로 수행하지 않는다.

- 사용자가 요청하지 않은 대규모 리팩터링
- 검수 과정에서의 코드 임의 수정
- 기존 기능 삭제
- 라이브러리 교체
- 데이터 구조 변경
- 백업 포맷 변경
- 테스트 삭제 또는 약화
- 확인하지 않은 환경을 정상으로 기록
- 추측을 사실로 기록
- 실제 운영 규칙이나 임상 규칙을 임의로 만들어 적용
- 실제 병원 데이터가 없는 상태에서 공식 규칙이라고 단정
- 검수 결과를 숨기거나 실패한 테스트를 생략

문제가 발견되면 먼저 영향과 근거를 보고하고 수정 여부를 사용자와 결정한다.

---

## 23. 검수 후 수정

사용자가 문제 수정을 요청하면 다음 순서를 따른다.

```text
문제 확인
↓
재현
↓
원인 분석
↓
영향 범위 확인
↓
최소 수정
↓
신규 기능 테스트
↓
회귀 테스트
↓
QA 보고서 갱신
↓
CHANGELOG 갱신
```

가능하면 문제의 원인을 확인한 뒤 수정한다.

증상만 임의로 덮는 패치를 피한다.

---

## 24. 최종 검수 절차

의미 있는 버전의 기본 검수 순서는 다음과 같다.

```text
① 현재 버전 확인
        ↓
② 직전 버전 및 변경사항 확인
        ↓
③ 현재 구조·데이터 흐름 확인
        ↓
④ 신규 기능 검수
        ↓
⑤ 기존 기능 회귀검수
        ↓
⑥ 저장·복원 검수
        ↓
⑦ 백업 검수
        ↓
⑧ 경계조건·오류조건 검수
        ↓
⑨ UI/UX 검수
        ↓
⑩ 테스트 결과 검토
        ↓
⑪ 문서-코드 일치 검수
        ↓
⑫ 문제 분류 및 심각도 지정
        ↓
⑬ QA_REPORT 작성
        ↓
⑭ CHANGELOG / 개발 기록 연결
        ↓
⑮ 다음 버전 회귀 기준선 반영 검토
```

프로젝트 규모가 커지면 필요한 단계를 더 세분화할 수 있다.

반대로 단순한 변경에는 전체 절차를 기계적으로 적용하지 않는다.

---

## 25. 최종 판정

QA 보고서의 최종 판정은 다음 중 하나를 사용한다.

### PASS

검수 범위에서 중대한 문제를 발견하지 못했고 주요 검증을 완료함.

### PASS WITH ISSUES

핵심 기능은 확인했으나 알려진 문제, 미검증 영역 또는 낮은 우선순위 문제가 남아 있음.

### BLOCKED

중요한 검증을 수행할 수 없어 최종 판단을 보류함.

### FAIL

핵심 기능 오류, 중대한 회귀, 데이터 손실 등으로 해당 버전을 다음 단계로 진행하기 어렵다고 판단함.

최종 판정은 검수 범위를 함께 기록한다.

---

## 26. 핵심 원칙 요약

이 프로젝트의 AI 검수는 다음 원칙을 따른다.

```text
새 기능이 된다
≠
프로그램이 정상이다

새 기능이 된다
+
기존 기능이 유지된다
+
데이터가 보존된다
+
오류 상황이 안전하다
+
문서가 실제 구현과 맞는다
+
검수 결과가 기록된다
=
검수된 버전
```

그리고 각 버전의 검수 결과는 다음 버전의 개발을 위한 지식으로 축적한다.

```text
개발
↓
검수
↓
기록
↓
기준선 강화
↓
다음 버전 개발
↓
검수
↓
기록
```

이 반복을 통해 프로젝트가 커질수록 코드뿐 아니라 검증 기준과 개발 기록도 함께 축적되도록 한다.
