# v0.7.3 회귀검수 기준선

문서 버전: 1.1
기준 버전: v0.7.3 RC
목적: 이후 버전에서 기존에 검증된 정상 동작과 핵심 데이터 보존 조건이 유지되는지 판단하기 위한 기준선

## v0.7.4 추가 기준 (2026-10-09)

아래 v0.7.3 계약에 다음 경계를 추가한다. 현재 결과는 `../TEST_REPORT.md` 기준이며 과거 실제 기기 결과를 새 결과에 합산하지 않는다.

| 보호 계약 | 자동 근거 | 브라우저 근거 |
| --- | --- | --- |
| 교체·삭제 확인 중 타 탭 변경 중단·보존 | state-integration 경합 3개+정상 1개 | UI의 확인 전 원본·revision 전달은 코드 검토; 경합 재현은 fake-indexeddb |

| ID·선임·override·월·날짜·듀티·이력·백업 연속 일관성 | state-integration 연속 저장/새 인스턴스/새 DB | 복수 월, 인원/배치, 실패/충돌, 복원 |
| 데이터·초안 분리와 이탈 취소·저장 실패 입력 유지 | 기존 저장/모델/Audit | discard, injected write failure, losing-tab draft |

자동 68개·브라우저 26개 통과는 Linux Chromium과 메모리 IndexedDB 범위다. 실제 휴대폰/iOS/Windows/공식 자료/A4는 미확인 상태를 유지한다.

## 1. 이 문서의 역할

이 문서는 v0.7.3 RC를 기준으로 이후 버전의 회귀(regression)를 검사하기 위한 기준선이다.

근거 범위: v0.7.3 RC 원본의 TEST_REPORT.md, CHANGELOG_v0.7.3.md, RELEASE_REPORT_v0.7.3.md 및 포함된 테스트/구조 파일을 대조하여 작성한다. 당시 테스트 보고서에 기록되지 않은 사항은 현재 정상 동작으로 추정하지 않는다.

여기서 기준선은 "모든 기능이 완벽하게 검증되었다"는 뜻이 아니다.

v0.7.3에서 실제 자동검사, PC 수동검사, 모바일 검사를 통해 확인된 범위를 구분하여 기록하고, 이후 버전에서 같은 기능이 유지되는지 비교하기 위한 것이다.

검증되지 않은 환경이나 범위는 정상 기준으로 승격하지 않는다.

이 문서는 `AI_QA_GUIDELINES.md`의 회귀검수 절차와 함께 사용한다.

## 2. 기준선의 검증 수준

각 항목은 다음 상태를 가질 수 있다.

- CONFIRMED: 실제 실행 또는 검증으로 확인됨
- CODE-VERIFIED: 코드 및 자동검사로 확인되었으나 실제 환경 검증은 제한됨
- UNVERIFIED: 아직 충분히 검증되지 않음
- BLOCKED: 환경 또는 도구 문제로 검증하지 못함

이 문서에서 "기준선으로 유지한다"는 표현은 이후 버전에서 최소한 동일한 동작이 깨지지 않아야 한다는 의미다.

# 3. Domain / 배치 계산 기준선

## RB-DOM-001 — 기존 배치 결과 유지

상태: CONFIRMED

v0.7.3의 독립 모델은 v0.7.0 FINAL 및 v0.7.2의 기준 결과와 비교하여 90개 샘플 날짜·듀티 조합의 배치 결과가 일치해야 한다.

이후 Domain 로직을 변경할 경우 기존 결과가 의도적으로 변경되는지 먼저 확인한다.

---

## RB-DOM-002 — 근무 코드 해석

상태: CONFIRMED

기본 근무 코드는 D / E / N / NC를 사용한다.

NC는 N으로 처리한다.

근무 코드와 시간 경계가 변경될 경우 기존 자동 배치 및 시각 선택에 미치는 영향을 함께 검수한다.

---

## RB-DOM-003 — 원본 인원 보존

상태: CONFIRMED

근무표를 해석할 때 원본 인원과 근무 행의 관계가 임의로 변하지 않아야 한다.

동명이인은 이름이 같더라도 별도의 ID를 유지한다.

이름 수정은 안정적인 인원 ID를 변경하지 않아야 한다.

---

## RB-DOM-004 — 추가·제외 인원은 원본을 직접 변경하지 않음

상태: CONFIRMED

추가 인원과 제외 인원은 저장된 원본 근무표 자체를 변경하지 않고 별도의 상태로 관리한다.

새 버전에서 이 구조를 변경할 경우 기존 근무표의 원본 보존과 배치 결과에 대한 회귀검수가 필요하다.

---

## RB-DOM-005 — 역할별 배치 규칙

상태: CONFIRMED

현재 기본 규칙에서는 선임 간호사와 반별 역할 설정을 기준으로 통보연락반·소화반·대피유도반을 구성한다.

현재 구조에서는 간호사 순서와 그룹 경계를 이용한다.

의사와 추가 사원은 대피유도반에 포함되는 현재 규칙을 유지한다.

실제 운영 규칙이 변경되는 경우 이는 단순 회귀 수정이 아니라 별도 요구사항 및 규칙 검증 대상으로 취급한다.

---

## RB-DOM-006 — 빈 대피유도반도 정상 상태로 표현

상태: CONFIRMED

특정 조건에서 대피유도반 인원이 4명보다 적거나 비어 있는 경우에도 모델이 해당 상태를 표현할 수 있어야 한다.

---

## RB-DOM-007 — 역할 변경 및 수동 배치 재연결

상태: CONFIRMED

인원의 선임 그룹 또는 역할이 변경되어도 안정적인 ID를 기준으로 기존 수동 배치가 가능한 범위에서 올바르게 재연결되어야 한다.

---

상태: CONFIRMED

상태: CONFIRMED

---

## RB-STO-007 — 근무표 교체 범위

상태: CONFIRMED

근무표 교체·삭제 시 해당 근무표의 인원 변경과 수동 배치가 적절히 초기화되되, 일반 변경 이력은 보존해야 한다.

상태: CONFIRMED

# 17. 기준선 승격 규칙

새로운 기능이나 중요한 시나리오가 충분히 검증되면 이후 버전의 기준선에 추가할 수 있다.

예:

```text
v0.7.4에서 확인
추가 인원
→ 수동 배치
→ 전체 백업
→ 복원
→ 수동 배치 유지

        ↓

중요 회귀 시나리오로 판단

        ↓

REGRESSION_BASELINE.md에 추가
```

모든 사소한 테스트를 기준선에 추가하지 않는다.

기준선은 프로젝트의 핵심 기능과 데이터 신뢰성을 보호하는 데 필요한 시나리오 중심으로 유지한다.

---

# 18. 기준선 변경 원칙

기준선에 있는 기능을 변경할 경우 단순히 기준선에서 삭제하지 않는다.

다음 내용을 함께 기록한다.

- 무엇이 바뀌었는가
- 왜 바뀌었는가
- 이전 동작과 새 동작의 차이는 무엇인가
- 기존 데이터에 영향을 주는가
- 이전 백업과 호환되는가
- 어떤 테스트가 추가되었는가
- CHANGELOG와 QA 보고서에 어떻게 기록되었는가

의도적인 동작 변경은 회귀 버그가 아니라 "요구사항/행동 변경"으로 구분할 수 있다.

---

# 19. 다음 버전 검수에서의 사용

다음 버전이 제공되면 AI는 이 문서를 기준으로 최소한 다음을 확인한다.

```text
v0.7.3 기준선
        ↓
새 버전 변경사항 확인
        ↓
영향받는 기준선 항목 식별
        ↓
자동 테스트 확인
        ↓
필요한 수동/실환경 검증 확인
        ↓
변경 없음 → PASS 여부 확인
변경 있음 → 의도된 변경인지 회귀인지 확인
        ↓
QA_REPORT에 기록
```

기준선에 없는 새 기능은 신규 기능 검수 대상으로 다룬다.

# 20. 기준선의 한계

이 문서는 v0.7.3의 검증 범위를 기록한 것이며, 프로그램이 임상적으로 승인되었음을 의미하지 않는다.

현재 프로젝트에는 인증·권한·중앙 서버·공식 병원 감사로그가 없으며, 실제 운영 규칙과 공식 양식도 아직 확정되지 않았다.

따라서 이 기준선은 소프트웨어의 기술적 안정성과 회귀 방지를 위한 기준이며, 실제 병원 운영 승인이나 임상적 타당성 검증을 대신하지 않는다.
